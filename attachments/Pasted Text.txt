From now on, handle all changes using the following process:

1. Treat GitHub as the authoritative source of truth. The chat, preview, deployment, and your memory are not substitutes for source control.

2. Before changing anything:

   - Confirm the current branch and commit hash.
   - Check for uncommitted changes.
   - Never overwrite, discard, or mix existing changes into new work.
   - Ensure the current working version has been committed and pushed.
   - For anything beyond a trivial text correction, create a clearly named branch.
   - Never work directly against the deployed production version.

3. Inspect before editing. Explain:

   - The current behavior
   - The likely cause of the problem
   - The exact files and functions involved
   - The intended correction
   - Possible effects on other systems
   - Possible effects on existing saved games
   - How the change will be tested

4. Make the smallest change that completely solves the requested problem.

   - Do not refactor unrelated code.
   - Do not rename unrelated functions or fields.
   - Do not replace entire files when a focused edit will work.
   - Do not change balance, styling, dependencies, configuration, or unrelated behavior unless explicitly requested.
   - Do not quietly fix additional issues. Report them separately.
   - Preserve existing working features.

5. Protect saved games and player data.

   - Do not remove, rename, or change the meaning of persisted fields without explicitly identifying the change.
   - If the save format must change, create a backward-compatible migration.
   - Test loading a save created before the change.
   - Never assume reverting source code will reverse changes already made to saved data.

6. Keep each change isolated.

   - One branch should address one clearly defined problem or feature.
   - Do not bundle unrelated improvements together.
   - Keep commits small and logically complete.
   - Do not include generated files, temporary files, credentials, local configuration, or unrelated edits.

7. Validate the change before calling it complete.

   - Run the relevant focused tests.
   - Run the complete test suite, including all tests under `src/game`.
   - Run typechecking.
   - Run a production build.
   - Directly test the affected behavior.
   - For simulation behavior, use fixed seeds and repeatable tests where possible.
   - Test both a new game and an existing save when applicable.
   - Report exactly which checks ran, which passed, which failed, and which could not be run.
   - Never say something is fixed if the required validation was skipped.

8. Before committing or deploying, show me:

   - Every changed file
   - A concise explanation of each change
   - Any save-format or migration changes
   - Any dependency or configuration changes
   - Any game-balance changes
   - Any remaining risks or unverified behavior
   - The final diff for review

9. Do not weaken tests to make a change pass. Do not delete failing tests unless the behavior they test has been explicitly and intentionally removed.

10. Wait for approval before deployment. Approval of the requested change does not automatically authorize unrelated changes or deployment.

11. After approval:

   - Commit only the reviewed changes.
   - Use a descriptive commit message.
   - Push the branch to GitHub.
   - Merge through the normal reviewed process.
   - Deploy only the exact reviewed commit.
   - Record and report the deployed commit hash.
   - Create a release tag for stable versions.

12. After deployment, perform a smoke test that verifies:

   - The application loads
   - Existing saves load
   - A new game can be started
   - Navigation works
   - The changed feature works
   - A normal game can be played or simulated
   - The deployed version matches the approved commit

13. If deployment verification fails:

   - Stop making additional production changes.
   - Report the failure clearly.
   - Roll back to the last verified working commit or release.
   - Confirm that rollback succeeded.
   - Diagnose the failure on a separate branch before attempting another deployment.

14. Never rely on this conversation to remember the previous working state, implementation decisions, deployment history, or rollback procedure. Preserve those in Git history and project documentation.

Follow this process for every future change unless I explicitly override a specific step.
